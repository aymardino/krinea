# Hosting on Render

Two editions share this repository.

## A · Krinea product (web + API + worker + PostgreSQL)

Service names in the blueprint (`tamis-*`) are internal identifiers kept from
the first deployment so that syncs do not recreate services; rename them in
the dashboard (Settings → Name) and in `render.yaml` together if you want them
to match the product name.

`render.yaml` at the repository root is a Render Blueprint. It declares a
PostgreSQL database (`tamis-db`), the API web service (`tamis-api`, Docker,
`apps/api/Dockerfile`), the background worker (`tamis-worker`, same image,
`python -m krinea_api.worker`) and the web front end (`tamis-web`, Docker,
`apps/web/Dockerfile`, Next.js standalone). Region: Frankfurt (EU). The API
and the worker run with `KRINEA_ENV=production`.

Browsers only ever talk to `tamis-web`: it proxies `/api/*` to `tamis-api`
over Render's private network (decision D-23), so the session cookie is
first-party and only one public address is needed, the default
`https://tamis-web-xxxx.onrender.com` or your own domain.

1. In Render: **New → Blueprint**, select the repository. Review the four
   services and the database, then **Apply**.
2. Public address, on two services (both required in production):
   - `BASE_URL` on `tamis-api`: the public https URL of the web app, for
     example `https://tamis-web-xxxx.onrender.com` or `https://example.org`.
     Sign-in links, invitations and Google redirects are built from it. This
     is a security setting: links sent by e-mail must never depend on what a
     request claims its address is. The blueprint declares it with
     `sync: false`, so you type the value once in the dashboard.
   - `PUBLIC_ORIGIN` on `tamis-web`: the same URL. It is the origin the proxy
     reports to the API. In production the proxy never reads it from client
     headers (`Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`); without
     `PUBLIC_ORIGIN` it falls back to `NEXT_PUBLIC_SITE_URL`, baked in at
     build time with the default `https://krinea.org`, which is only right
     for the official hosted service. The Google callback URL is built from
     this origin, so keep the two values identical.
3. `SECRET_KEY` is generated by Render on `tamis-api` and shared with the
   worker and with the web proxy (`PROXY_KEY`). Leave it as is. With
   `KRINEA_ENV=production` the API refuses to start when `SECRET_KEY` is
   empty, shorter than 16 characters or a placeholder (`change-me`,
   `change-me-in-production`, `dev-secret-change-me`).
4. E-mail on `tamis-api` (sign-in links and invitations), see
   [E-mail](#e-mail) below. Until it is configured, password and Google
   sign-in work, the sign-in page hides the e-mail-link option and
   invitations fail with a `502` that gives the reason.
5. PDFs, see [Where PDFs are stored](#where-pdfs-are-stored) below: with the
   worker running, set the `S3_*` variables on `tamis-api` and
   `tamis-worker`.
6. Optional secrets marked `sync: false`: `ANTHROPIC_API_KEY` /
   `GEMINI_API_KEY` / `DEEPSEEK_API_KEY` for included AI credits (API and
   worker), `UNPAYWALL_EMAIL` for the open-access PDF lookup, and
   `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` for "Sign in with Google"
   (authorised redirect URI `<BASE_URL>/api/auth/google/callback`).
7. Open the `tamis-web` URL and create an account. Every API setting is
   listed in `apps/api/README.md`.
8. Deploys: every push to `main` redeploys; preview environments can be
   enabled per pull request. Rollback from the service's **Events** page.
9. Database: Render takes daily backups on paid PostgreSQL plans; export with
   `pg_dump` for off-site copies. Render's connection string (`postgres://…`)
   is accepted as is; the API rewrites it for the psycopg driver.

The worker also does the housekeeping: at most once an hour it deletes
sign-in-link tokens older than a day and sessions past their expiry. A setup
without a worker (`INLINE_JOBS=1`) does not run that purge.

Values you set in the dashboard survive Blueprint syncs only for variables
the blueprint marks `sync: false` and for variables it does not list at all.
A variable with a fixed `value` in `render.yaml` is reset to that value on
every sync.

### E-mail

With `KRINEA_ENV=production` the API sends e-mail only through a real
provider: `EMAIL_PROVIDER` must be `smtp` or `resend` with complete settings.
With the default `console`, or with missing settings, it refuses to send:
a sign-in link request or an invitation answers `502` with the reason (also
written to the API logs), and the sign-in page hides the e-mail-link option
because `/api/auth/providers` reports e-mail as unavailable. A delivery the
provider rejects (wrong password, host unreachable) is also a `502` with the
reason, never a silent success. Password sign-up and Google sign-in need no
e-mail.

**SMTP** (any mailbox): `EMAIL_PROVIDER=smtp`, `SMTP_HOST`, `SMTP_PORT`
(default `587`), `SMTP_USER`, `SMTP_PASSWORD`, optionally `EMAIL_FROM`.
Port `465`, or `SMTP_TLS=ssl` on another port, uses implicit TLS; otherwise
the connection is upgraded with STARTTLS. Without `EMAIL_FROM` the sender is
the mailbox itself (`Krinea <SMTP_USER>`), which is what most providers
require: they only relay mail sent from the authenticated address or its
aliases.

- OVHcloud mailbox on your domain (what the hosted service at krinea.org
  uses; OVHcloud, France, EU):

  ```
  EMAIL_PROVIDER=smtp
  SMTP_HOST=ssl0.ovh.net
  SMTP_PORT=465
  SMTP_USER=no-reply@example.org
  SMTP_PASSWORD=<the mailbox password>
  EMAIL_FROM=Krinea <no-reply@example.org>
  ```

- Gmail, when you have no domain yet (about 500 messages a day):

  ```
  EMAIL_PROVIDER=smtp
  SMTP_HOST=smtp.gmail.com
  SMTP_PORT=587
  SMTP_USER=you@gmail.com
  SMTP_PASSWORD=<16-character Google app password>
  EMAIL_FROM=Krinea <you@gmail.com>
  ```

  Google: Account → Security → 2-step verification → App passwords. The
  normal account password does not work over SMTP.

**Resend** (alternative): `EMAIL_PROVIDER=resend`, `RESEND_API_KEY` and
`EMAIL_FROM` on a domain verified in Resend.

### Where PDFs are stored

- **S3-compatible bucket** (Cloudflare R2, Backblaze B2, OVHcloud Object
  Storage…): set `S3_BUCKET`, `S3_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID` and
  `AWS_SECRET_ACCESS_KEY` (and `S3_REGION` if the provider needs one) on
  both `tamis-api` and `tamis-worker`. This is required whenever the worker
  runs, because the worker reads the PDFs for AI screening and extraction
  and a Render disk belongs to one service only.
- **Persistent disk**: only for a setup with `INLINE_JOBS=1` on `tamis-api`
  and no worker. Attach a disk to `tamis-api` at `/data` (paid instance,
  single instance) and leave `S3_BUCKET` empty.

Deleting a review, records or an import also deletes their PDFs, from the
bucket or from the disk.

### Custom domain

1. Buy the domain at a registrar (Cloudflare Registrar, Porkbun, OVHcloud,
   Gandi…).
2. In Render, `tamis-web` → **Settings → Custom domains → Add**: enter the
   apex (`example.org`) and Render also proposes `www`. It shows the DNS
   records to create at the registrar: an `A` record for the apex to Render's
   IP and a `CNAME` for `www` to the `onrender.com` host. On Cloudflare DNS,
   keep the records "DNS only" (grey cloud) until the certificate is issued.
3. Wait for **Verified** and the certificate (minutes to an hour). Nothing
   needs an `api.` subdomain: the API stays behind the web app's `/api`.
4. Set `BASE_URL` on `tamis-api` and `PUBLIC_ORIGIN` on `tamis-web` to
   `https://example.org`. Links in e-mails then always use the domain, even
   for requests that reach the old `onrender.com` host. For canonical URLs,
   the sitemap and social cards, also set `NEXT_PUBLIC_SITE_URL` on
   `tamis-web` and redeploy with **Clear build cache & deploy** (the value is
   baked in at build time).
5. Use a sender on the domain (`EMAIL_FROM`, see [E-mail](#e-mail)) and
   update the Google OAuth redirect URI to
   `https://example.org/api/auth/google/callback`.

### Contact address on the site

The site shows `contact@krinea.org` unless `NEXT_PUBLIC_CONTACT_EMAIL` is
set on `tamis-web`. On your own deployment, set it to your address, then
**Manual Deploy → Clear build cache & deploy**: the value is baked into the
pages at build time.

### If something fails

- **"Server failure" mails / `tamis-api` restarting**: open the service's
  **Logs**. A traceback at startup means a bad environment variable: most
  often `DATABASE_URL`, or a `SECRET_KEY` the production guard refuses (the
  message says why). `/health` must answer `{"ok": true, ...}`.
- **"The API is not reachable"** (a `502` from `/api/...`): `tamis-web`
  cannot reach the API. The response body names the `target` it tried and
  the error `code`; the same line is in `tamis-web`'s logs. Check, in this
  order: `tamis-api` shows **Deployed** (not "Failed deploy"); `API_URL` on
  `tamis-web` → **Environment** is the API's private address
  (`tamis-api-xxxx:10000`), not empty and not `localhost`. Blueprint
  references are filled in at sync time, so if the API failed to build during
  the first sync, click **Manual sync** on the Blueprint once it is green.
  Free instances cannot receive private traffic: with `plan: free`, set
  `API_URL` to the API's public `https://….onrender.com` URL instead.
- **"Something went wrong"** elsewhere: open the browser's network tab and
  read the failing `/api/...` response. A `401` right after signing in means
  the session cookie did not come back: `COOKIE_SECURE` must be `true` only
  behind HTTPS.
- **No e-mail arrives, or the e-mail-link option is missing**: read
  [E-mail](#e-mail). The `502` returned by the invitation or the sign-in
  link request names the cause; `/api/auth/providers` shows whether the API
  considers e-mail available.
- **Links in e-mails or the Google redirect point to the wrong host**:
  `BASE_URL` on `tamis-api` or `PUBLIC_ORIGIN` on `tamis-web` is missing or
  different from the address people use.
- **Blueprint sync errors on `fromService`**: replace the reference with a
  plain `value` (the API's public URL for `API_URL`, the API's `SECRET_KEY`
  for `PROXY_KEY`) and sync again.

Costs scale with instance sizes; three Starter services plus the entry
PostgreSQL plan are in the tens of dollars per month. For a test, the
comment at the top of `render.yaml` describes a cheaper layout (free
instances, `INLINE_JOBS=1`, no worker, so a disk or a bucket for PDFs). Check
render.com/pricing.

## B · Streamlit edition (single container)

The root `Dockerfile` builds the original Streamlit workbench
(`review_app.py`) with SQLite in `/data`. It copies `packages/core` into the
image and installs it through `requirements.txt`, so build it with the
repository root as the context. Deploy it as one Docker web service with a
persistent disk at `/data`, environment `DATA_DIR=/data`, `APP_LANG` and
optional provider keys. Health check `/_stcore/health`. Put it behind
Cloudflare Access or similar: Streamlit has no login.

## C · Anywhere else

`docker compose up --build` runs the full product on one machine
(PostgreSQL, API, worker, web) with `.env` from `.env.example`. Set
`SECRET_KEY` in `.env` first: compose stops with a message when it is
missing, and the API refuses a short or placeholder value. Set `BASE_URL` to
the address people use; compose passes it to the web proxy as
`PUBLIC_ORIGIN`. The same images run on Fly.io, Railway, a VPS or a
university server.
